# Known limitations

Schedule AI Voice submission v1 is a **student / demo system**, not a production
deployment. Everything runs on one machine against a local model and local
SQLite. This page states what it does not do, and where it is measurably
imperfect, so nothing below has to be discovered.

## Scope limits (not implemented)

| Area | Status |
|---|---|
| **Telephony** | No real phone calls. Calls, SMS and voice are handled by deterministic in-process providers (`src/providers/`). There is no speech-to-text or text-to-speech. |
| **Calendars** | No Google or Outlook integration. Availability and calendar writes use deterministic doubles; no real calendar is ever changed. |
| **Authentication** | No production authentication or session management. |
| **Multi-tenancy** | The data model is organisation-scoped, but tenant isolation is not enforced as a production security boundary. |
| **Deployment** | No deployment infrastructure; it is run locally with `npm` scripts. |
| **UI** | No user interface; the demos are command-line programs. |

## Model and language limits

- **`qwen2.5:7b-instruct` is the current English demo model**, chosen from a
  five-model local benchmark run at `num_ctx` 16384 on an 8 GiB GPU
  (`docs/FOUNDER_REVIEW_MISSION_2_LOCAL_BRAIN.md`). Model choice is not final and
  the `LlmProvider` port allows replacing it.
- **Hebrew conversation is experimental.** Hebrew *scheduling understanding*
  (e.g. resolving "מחר בשלוש" in the contact's timezone, refusing what cannot be
  resolved) is covered by deterministic tests. But no evaluated local model yet
  produces production-quality Hebrew conversation: the most fluent candidate
  (`aya-expanse:8b`) had tool-call formatting problems, and the reliable ones do
  not sound native.
- **Model behaviour varies run to run.** For example, given "call me back at 3"
  the model sometimes asks "3 in the afternoon?" instead of booking immediately;
  the demo handles this and reports it as an observation.

## The claim gate is defense in depth, not a guarantee

A language model can say "your meeting is booked" when nothing was booked. Every
customer-facing reply therefore passes a claim gate: a rule-based detector plus a
semantic verifier (the local model asked only to classify), with each detected
claim checked against what was actually persisted. Unsupported claims are
regenerated by the model; if that keeps failing the turn is handed to a person.
Malformed or timed-out verifier output fails closed.

**It is not proven perfect.** Measured with `qwen2.5:7b-instruct` as the verifier
on sentences it was **not** tuned on:

| Test set | Unsupported claims missed by both layers | Honest replies wrongly flagged |
|---|---|---|
| Repository held-out split (96 claims / 82 honest) | 3 (3.1%) | 14.6% |
| Independent QA set (23 claims / 17 honest) | 6 | 11.8% |
| Operator sealed set (64 claims / 30 honest) | 7 (10.9%) | 0% |

The misses are mostly **indirect** claims ("You're now connected with a member of
our team", "The 2pm slot on Thursday is yours", "We'll see you on Thursday at
2pm"). A wrong flag on an honest reply costs one regeneration, not a wrong
message. Because this is a demo with no real customers, no real calls and no
real calendar writes, a missed claim cannot cause a real-world effect here — but
this limitation must be solved before any production use. Details:
`docs/MISSION_2F_SEMANTIC_VERIFIER.md`, `docs/MISSION_2G_VERIFIER_ROUND.md`.

**Latency cost:** the semantic verifier adds roughly 0.9–1.2 s per
customer-facing reply (p50 about 1.0 s on an RTX 4060 Laptop GPU). Realtime voice
would need this optimised.

## Future improvements

- Claim verification: clause-level verdicts or narrower per-clause questions
  (proposed in `docs/MISSION_2G_VERIFIER_ROUND.md` §10.3).
- A Hebrew-capable local model, possibly routed per language through the existing
  `LlmProvider` port.
- Real telephony, speech and calendar providers behind the existing ports.
- Authentication, tenant isolation and deployment.
